Chrome Web Store Publishing Strategy & Architecture Guide

Comprehensive blueprint for releasing all 10 Qeloma extensions on the Chrome Web Store. Explains how to leverage 1 pnpm monorepo to generate 10 individual, distinct CWS store listings with unique App IDs.

gavel Critical Architectural Mandate: 1 Store Listing per Extension
cancel What CANNOT be done

You **cannot** bundle all 10 tools into a single Chrome extension ZIP and ask users to install one massive 50MB extension. Chrome Web Store policies mandate **Single Purpose Policy** (Rule 2.2) and will reject extensions that attempt multi-tool bloat.

check_circle What MUST be done (The Qeloma Solution)

Each of the 10 extensions gets its **own store listing and unique App ID** (e.g. pfhkja...). Maintain them cleanly in **1 pnpm Monorepo**, and build 10 lightweight ZIP files to upload to your single $5 Chrome Developer Account!

policy Manifest V3 Safety, Review Speed & Permission Tiers

Chrome Web Store review times depend heavily on the requested MV3 permissions. We split the 10 Qeloma tools into 2 permission buckets to maximize fast reviews:

flash_on Green Permission Tier (Fast Track) < 24h Review

Permissions used: activeTab, storage, contextMenus.

These tools (e.g., Qeloma Shot, Reader, Inspect) do NOT require persistent host permissions, enabling automated/fast review within hours!

verified Amber Permission Tier (Standard Review) 1 - 2 Days Review

Permissions used: scripting, tabs, offscreen, webNavigation.

These tools require human review for DOM modification or tab listening. They strictly adhere to minimal privilege principles.
